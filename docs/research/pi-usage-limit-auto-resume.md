# Resume Pi sessions after subscription usage limits reset

Investigated 2026-11-26 on Pi 1.6.1 and the local Claude bridge. **Design: enable auto-resume by default for the Claude bridge. Wait for a provider-reported reset and start one clearly labeled continuation in the same Pi session.** No provider polling or Pi core changes are needed. These are the research and design notes; see the [extensions README](../../home/.pi/agent/extensions/README.md) for configuration and behavior.

## What happened in our sessions

I scanned terminal assistant errors in 141 local Pi session JSONL files modified in the preceding 30 days. Seven `claude-bridge` errors in three sessions had the normalized quota signature. All seven were on November 26, on `claude-opus-5-5`, and all named `five_hour`. Two of the three sessions were registered orchestration workers. The records cluster around two shared deadlines, not seven separate exhaustion events:

| Failures around (UTC) | Reported reset (`America/New_York`) | Reset in UTC | Observed |
| --- | --- | --- | --- |
| 07:38–07:42 | 5:40 a.m. | 10:40Z | Four failures, two sessions. One followed a recorded tool result; the same session next recorded a user turn at 12:00:43Z and Claude started calling tools again. |
| 13:53 | Noon | 17:00Z | Three failures, two sessions. |

The stable error prefix was `Claude quota exceeded — rate limit (five_hour)`. Claude's original text followed it: `You've hit your 5-hour limit · resets 12pm (America/New_York) · out of usage credits`. That last clause means Extra Usage wasn't available **for this refusal**; it does not negate the explicitly reported subscription reset. I found no weekly failure or confirmed Codex subscription exhaustion in this sample (39 terminal `openai-codex` errors, none reported a quota reset). It is not an account-history audit.

Local sources, abbreviated JSONL filenames and line numbers: `2026-11-26T05-32-45-695Z_01a21657…` lines 474–486, 747–748, 1025–1029; `2026-11-26T07-24-27-975Z_01a216bd…` line 167; `2026-11-26T13-09-40-328Z_01a217f9…` line 302. The persisted errors have readable times but no machine-readable reset field. I used the timezone in the original text to make the table, not as a proposed parser.

## What T3 Code does

Your recollection was right. T3 Code [normalizes provider failures](https://github.com/pingdotgg/t3code/pull/12677) to a `usage_limit` class with an optional reset timestamp. Its [opt-in recovery feature](https://github.com/pingdotgg/t3code/pull/12686) stores a recovery schedule against the failed run. A [server worker](https://github.com/pingdotgg/t3code/blob/fce54e67a6a71aa4523ea9ccb2f4d2b3e287d390/apps/server/src/orchestration-v2/UsageLimitRecoveryWorker.ts) reads that state and dispatches **“Continue where you left off.”** as a server-authored message in the same thread. It does not replay the original prompt. It doesn't need a connected client, and guards against stale dispatch after cancellation, a newer run, and other state changes. Unknown resets are manual. Follow-up fixes verify [child completion still reaches its parent](https://github.com/pingdotgg/t3code/pull/29838) and [re-arm a dispatch after restart only if its provider run never began](https://github.com/pingdotgg/t3code/pull/31292).

Two details are worth borrowing or improving on:

- The [Claude adapter](https://github.com/pingdotgg/t3code/blob/fce54e67a6a71aa4523ea9ccb2f4d2b3e287d390/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts) reads `rate_limit_event` and distinguishes a real block from a rejected plan window with working overage. The [Codex adapter](https://github.com/pingdotgg/t3code/pull/27791) can fill in a missing reset with one bounded `account/rateLimits/read` request. I would not add ongoing usage polling for Pi's first version; [T3's early-resume polling proposal](https://github.com/pingdotgg/t3code/pull/24511) was closed unmerged.
- [T3 issue #22026](https://github.com/pingdotgg/t3code/issues/22026) documents real refusals seconds after the advertised reset. The pinned worker fires at the reset and rejects an already-expired timestamp on a fresh failure, so one refusal can strand the thread. Use a small grace period and one bounded retry rather than firing at the exact second or ignoring a repeated reset.

**Other prior art.** [Claude Code itself](https://code.claude.com/docs/en/interactive-mode#wait-for-a-usage-limit-to-reset) does this natively in interactive subscription sessions (v2.1.234+). It prompts Claude to continue rather than resending the original message. The installed 2.1.331 binary contains the exact text: “Your claude.ai usage limit has reset. Continue the task you were working on when the limit was reached; do not repeat work that is already complete.” Pi intentionally uses only `Continue.`. Its wait is not offered in background or `-p` runs; it won't automatically arm a reset more than 24 hours out, and exiting loses the wait. The bridge's SDK stream demonstrably returns the failure to Pi instead. The [Paseo plugin](https://github.com/babo-jeonguk/paseo-usage-auto-resume) is a daemon-backed example with saved reservations and optional account-usage checks. [Unsnooze](https://github.com/saaranshM/unsnooze) combines hook/transcript/terminal detection with a daemon that can reopen a closed session. Its process management solves a broader problem than resuming a live Pi pane.

## The Pi path

**Claude already supplies the right input.** The [Agent SDK](https://code.claude.com/docs/en/agent-sdk/typescript) emits `rate_limit_event` with `rate_limit_info.status`, `rateLimitType`, `resetsAt` (epoch seconds), and overage fields. The [bridge forwards the raw stream event](../../home/.pi/agent/extensions/claude-bridge/src/index.ts#L1588), pairs a rejection with the SDK error result, and normalizes the terminal error. It also projects the reset, window and status into [synthetic Anthropic response headers](../../home/.pi/agent/extensions/claude-bridge/src/rate-limit.ts). Those headers deliberately use HTTP **200** and do not carry all the raw overage fields, so a 429-only detector won't work. The extension uses normalized metadata attached by the bridge to the failed assistant response when it pairs the rejection with the SDK error result. It doesn't have to correlate a separate raw event or parse the terminal clock. `five_hour`, `seven_day`, and the model-specific weekly windows can use the same scheduling code; a live weekly refusal still needs verification.

**Can we advance the turn without another message?** Not through the supported extension API after settlement. Pi's low-level [`Agent.continue()`](https://github.com/earendil-works/pi/blob/v1.6.1/packages/agent/src/agent.ts) rejects a transcript ending in an assistant message, including the persisted error. `agent_before_settle` can request an *immediate* continuation with suitable context; it isn't a delayed retry API, and blocking the hook for hours would leave Pi busy. Use a tagged, displayed custom message with `pi.sendMessage(..., { triggerTurn: true })`. Pi stores this as extension-authored, not a typed user entry, and sends the text to the model as user-role input. This uses normal run preparation and doesn't submit anything from the editor. The old `before_agent_start` caveat in the bridge's prompt-capture diagnostics was fixed in [Pi 1.2.0](https://github.com/earendil-works/pi/releases/tag/v1.2.0). Sources: [Pi 1.6.1 extension API](https://github.com/earendil-works/pi/blob/v1.6.1/packages/coding-agent/docs/extensions.md), [run preparation](https://github.com/earendil-works/pi/blob/v1.6.1/packages/coding-agent/src/core/agent-session.ts), [message conversion](https://github.com/earendil-works/pi/blob/v1.6.1/packages/coding-agent/src/core/messages.ts).

**Codex Plus does have a five-hour allowance; weekly limits may also apply.** [OpenAI's pricing docs](https://developers.openai.com/codex/pricing) say usage varies by model and task; API-key billing is separate. T3 uses [Codex App Server](https://developers.openai.com/codex/app-server), which exposes account rate limits. Pi instead talks directly to [Codex Responses](https://github.com/earendil-works/pi/blob/v1.6.1/packages/ai/src/api/openai-codex-responses.ts). Pi forwards parsed SSE/WebSocket events before normalization, but the HTTP error parser can turn the JSON body (and exact `resets_at`) into display text. Capture narrowly scoped evidence at the next real exhaustion: the raw error code/reset and the blocking window, from the stream event or HTTP headers if present. [OpenAI's error mapping](https://github.com/openai/codex/blob/main/codex-rs/codex-api/src/api_bridge.rs) and [header/event parser](https://github.com/openai/codex/blob/main/codex-rs/codex-api/src/rate_limits.rs) give candidate shapes. If our HTTP path only exposes a generic 429 plus prose, leave it manual until Pi exposes the typed error. Do not substitute an unrelated Codex App Server login or guess five hours from the failure time.

## First-version design

1. **Arm after settlement.** In a separate `usage-limit-resume` extension, require a confirmed, time-based subscription block with a valid absolute reset on the actual terminal assistant error. Do it at `agent_settled`, not `agent_end`, so Pi's retries, fallback, and queued work get first chance. No schedule on warnings, successful overage, manual abort, normal API throttling, outage, auth failure, billing-only cap, or unknown reset.
2. **Wait without making requests.** Persist a small `pi.appendEntry()` record on the active session branch: failed assistant entry ID, provider/model and limiting window, reset and attempt IDs, retry count and state. Keep a cancellable timer with a wall-clock check after sleep. Start with reset + 120 s and small jitter for sibling workers sharing an account. If that attempt returns the same reset, allow one delayed retry, then stop visibly. If a different window really blocks the attempt, schedule its reported reset, subject to a total cap. Enable the provider once via configuration (`claude-bridge` by default), and show the deadline and a cancel command. No automatic credit purchase, account rotation, or model change.
3. **Revalidate on wake.** Require the same active session/branch, unchanged relevant conversation, same model selection, no conflicting run or pending permission/approval, and a still-armed job. Cancel on a manual prompt, model change, branch/session change, or explicit cancel. Anchor to the failed conversation entry, not the literal latest JSONL record: extensions such as PR Watch append metadata while idle. Persist dispatch state and tag the continuation with the attempt ID; reconcile it with the transcript before any restore. Don't blindly resend an attempt whose dispatch is ambiguous after a crash. A Pi extension can restore on `/reload` but cannot wake a closed Pi process. A clean quit cancels the wait. A Herdr or daemon launcher is a separate phase if that becomes a requirement.
4. **Resume the work, not the original request.** Send one custom message containing **`Continue.`**, with the label **Pi usage limit resumed** rendered separately. Keep permissions unchanged. For orchestration, expose the scheduled resume as a paused worker, not a successful settlement. [PR Watch currently publishes the latest assistant response on settlement](../../home/.pi/agent/extensions/pr-watch.ts#L1194), including error text. Deliver orchestration messages normally even during a quota wait. A new run supersedes the old timer; if that run hits quota again, it can schedule a new wait.

**Verification so far:** 21 existing bridge rate-limit and error-result tests passed offline. A separate isolated Pi 1.6.1 smoke test with a faux provider confirmed that bare `continue()` rejects after an assistant error, while a tagged idle custom message runs `before_agent_start` and continues the same transcript without a second typed-user entry. The implementation adds an offline Pi runtime test that fails after a completed tool call, advances the scheduler, and verifies the tool result is still in context and the harness hasn't re-executed the tool. It also tests weekly waits, repeated refusals, reload/deduplication, and worker notices. No real subscription reset was exercised. Retaining context is not a guarantee the model will never choose to repeat a side effect.
